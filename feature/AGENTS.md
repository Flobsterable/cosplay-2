# Общие правила feature UI

Эти правила дополняют корневой AGENTS.md для всех feature-модулей.
Структура ниже целевая: существующие файлы пока могут лежать в корне пакета.

## Декомпозиция UI и подпапки

- Новый или существенно перерабатываемый UI размещай внутри feature-пакета
  в `ui/<экран>/`: Screen — в корне папки экрана, его самостоятельные блоки —
  в `ui/<экран>/components/`. Компоненты нескольких экранов одного feature
  размещай в `ui/components/`. Например: `ui/catalog/FestivalListScreen.kt`,
  `ui/catalog/components/FestivalFilters.kt`, `ui/components/FestivalCard.kt`.
  Пакеты должны соответствовать подпапкам. Это целевая структура; существующие
  файлы пока находятся в корне feature-пакетов.
- Screen отвечает за каркас экрана, выбор ветви UI-состояния и соединение
  компонентов. Панель фильтров, карточку, секцию деталей, диалог и другие
  самостоятельные смысловые блоки выноси в именованные composable-функции.
  Выделяй компонент также при повторном использовании или собственной логике
  взаимодействия; не жди, пока экран станет большим.
- Самостоятельный компонент размещай в отдельном файле с его именем. Небольшие
  private helpers, обслуживающие только этот компонент, можно оставить рядом.
  Не собирай несвязанные компоненты в растущий `*Components.kt` и не дроби каждый
  Text/Spacer в отдельный файл. Граница определяется ответственностью, а не
  формальным лимитом строк.
- Компонент получает только нужные ему данные и callbacks, предоставляет
  `modifier: Modifier = Modifier` для корневого элемента. Не передавай весь
  state holder или repository ради одного значения/действия. Общее состояние
  остаётся у ближайшего общего владельца; выделение компонента не должно
  дублировать состояние или менять ключи effects/rememberSaveable.
- Используй минимальную видимость: private для helpers файла, internal для
  компонентов внутри модуля; публичными оставляй нужные внешним модулям точки
  входа. Перед выделением проверь существующие компоненты. При работе с большим
  экраном декомпозируй затронутые блоки; перенос остальных экранов выполняй
  отдельной задачей. Компиляция не подтверждает внешний вид: ручную проверку
  Android/Desktop и её отсутствие указывай отдельно.

## Тема, доступность и списки

- Используй MaterialTheme для цветов, типографики и форм. Общую дизайн-систему
  размещай по правилам core/ui в `core/AGENTS.md`, не дублируй её в feature.
- Интерактивные иконки имеют понятные подписи из ресурсов; декоративные —
  contentDescription = null. Отражай выбранное/недоступное состояние семантикой,
  не только цветом. Сохраняй фокус и управление клавиатурой на Desktop.
- Изменяемые Lazy-списки получают стабильные уникальные key по идентичности
  элемента, а не индексу. Сохраняй положение прокрутки при возврате в тот же
  контекст; сброс при изменении фильтров определяется контрактом сценария.
- Не выполняй тяжёлую сортировку/фильтрацию на каждой рекомпозиции. Выбирай
  use case для бизнес-правил, remember с полными ключами для UI-вычислений;
  не кэшируй результат без учёта меняющихся данных и параметров.
- Проверяй длинные тексты, увеличенный шрифт, узкое окно, светлую/тёмную тему.
  Не задавай фиксированную высоту текстового блока, скрывающую содержимое.
  Компиляция не заменяет ручную проверку; перечисляй невыполненные проверки.
- Строковые ресурсы, use cases, отмена и защита от повторных действий определены
  в корневом AGENTS.md. Не добавляй отдельную реализацию этих механизмов в компонент.
