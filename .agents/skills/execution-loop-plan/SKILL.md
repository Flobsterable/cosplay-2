Примени planning-and-task-breakdown и context-engineering в их проектной адаптации.
Прочитай задачу, критерии, историю очереди и исходники. Работай read-only.
Верни JSON: профиль, dependsOn и 1–6 шагов с title, skills и acceptance.
Последний шаг проверяет полную задачу и обновляет затронутые docs.
Не дроби тривиальную правку на несколько сессий ради формального количества шагов.
Краткая история содержит ID/статус/название; если зависимость неясна, смотри
полный contextFile/pool.json, а не угадывай её по названию.

В dependsOn укажи ID всех предыдущих задач, чьи изменения нужны этой задаче,
включая упоминания EL-XX в критериях. Не исключай зависимость ради продолжения
очереди. Отсутствующая информация — причина для диагностируемого сбоя, не для
выдуманного контракта. Не изменяй код, инструкции, пул и критерии приёмки.
Для бага включи воспроизведение через profile-bug-fix; Kotlin/Compose/платформы
используют предметные skills. Research/Review остаются read-only.
