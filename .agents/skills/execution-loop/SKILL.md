# Execution Loop

В Cosplay 2 прочитай `docs/ai-agent/execution-loop/README.md` и `source.json` рядом.
Источник задаётся source.json: GitHub Issues или Notion. Текущий пул — Notion.
Для Notion transport=mcp-snapshot перед новым независимым пулом прочитай схему
collection://<dataSourceId> через fetch, получи все строки query_data_sources,
сохрани JSON {dataSourceId, exportedAt, has_more:false, results:[...]} в новый
snapshotFile под build/execution-loop и укажи путь в source.json. Не перезаписывай
снимок уже начатого эксперимента. Только поле «Готово к работе», нужные проект/пул.
Не собирай snapshot по памяти: используй фактический ответ Notion. При пагинации
собери все страницы; transport=rest требует NOTION_TOKEN вне Git.
Для сравнения прогонов сначала выполни `fetch` и передавай один сохранённый
снимок всем прогонам. Локальный tasks.json — пример, используй его только явно.
При недостаточном числе Issues или ошибке загрузки не подменяй очередь примером.
Запрос подготовить/доработать механизм не означает запуск измеряемых прогонов.
При запросе запуска используй `scripts/execution-loop.mjs`, а не ручной обход пула.
Перед запуском нужны чистый отдельный checkout и провайдер. Облако без аргумента
модели наследует настройку Codex; для сравнения укажи точный ID, локально он обязателен.
Прочитай publication.json: draft-pr разрешает runner создавать ветки, push и draft PR
на проверенные задачи в рамках уже авторизованного пользователем запуска.
Выполни preflight до платных вызовов. Публикация — линейная цепочка PR;
она имеет ограниченные повторы без модели, постоянный сбой останавливает очередь.
При каждом появлении PR в artifacts.json вызывай mcp__codex_app__attach_artifact
с artifact_type=pull_request и URL. Обязательно обработай все ссылки также после
ошибки/завершения прогона. Не считай запись URL в файл прикреплением к чату.
Не очищай чужую работу. Если отдельный checkout надо создать, соблюдай разрешения
на ветки/worktrees из текущей задачи и AGENTS.md.

Runner ведёт очередь, но не выполняет большую задачу одной сессией.
Для каждой задачи он запускает отдельные сессии и навыки:

- `execution-loop-plan` — read-only план, профиль, зависимости и 1–6 проверяемых шагов.
- `execution-loop-step` — один шаг, предметные навыки, отдельный контекст и проверки.
- `execution-loop-recover` — диагноз, ограниченное исправление, retry/skip/stop.
- `execution-loop-review` — отдельная read-only сессия после проверок и до коммита.

Экономия задаётся docs/ai-agent/execution-loop/economy.json: у Markdown-задач
план строится локально, исполнение и независимое ревью сохраняются. У остальных
задач планировщик вызывается отдельно. Короткие SKILL.md загружаются обычно;
полные references/upstream-reference.md — только для конкретного вопроса.
Полные context.json и журналы доступны по ссылкам, не копируй всю историю в ответ.
Остановка по Budget не запускает ещё один платный вызов обработчика.

Этапы опираются на проектные адаптации Agent Skills Addy Osmani:
planning-and-task-breakdown, incremental-implementation, context-engineering,
debugging-and-error-recovery и code-review-and-quality. Версия и происхождение
зафиксированы в docs/ai-agent/execution-loop/upstream-skills.json.
Предметные Kotlin/KMP skills и профильные правила сохраняют силу.

Каждая задача исполняется в отдельном detached worktree. Только полностью
проверенный и одобренный независимым ревью результат коммитится и переносится в основной checkout.
В режиме draft-pr DONE требует также подтверждённого draft PR. Незавершённые
patches и все свидетельства остаются в рабочих копиях под каталогом прогона.
Завершение одной CLI-сессии не считается паузой, если runner сам начинает следующую.
Профиль Research/Review остаётся read-only: передача результата следующему этапу
не разрешает редактирование внутри этого профиля. Фича, рефакторинг и тесты используют
предметные skills; отдельного существующего профиля «Feature» в проекте нет.

Не обходи BLOCKED и не ослабляй проверки ради рекорда. При сбое сохраняй patch,
логи и причину. Обработчик может исправить сбой и повторить шаг (максимум дважды)
или отложить локально заблокированную задачу. Зависимые задачи блокируются,
независимые продолжаются. Неисправимый общий сбой останавливает очередь;
повтор fingerprint общей ошибки после восстановления срабатывает как предохранитель.
Дефект runner диагностируется с остановкой: текущий процесс не переписывает себя.
Не исправляй инструкции
во время замеряемого прогона. Улучшение правил выполняется между прогонами,
по фактическому падению и с неизменным пулом/исходным кодом.

В финале дай минуты без пауз, число последовательных DONE, точку остановки,
ограничения проверок и путь к отчёту. Не подставляй подготовку, dry-run или тест
runner вместо времени работы модели. Локальный результат допустим только после
реального запуска указанной модели через Ollama/LM Studio.
