# Два уровня проверки Cosplay 2

В репозитории Cosplay 2 прочитай `docs/testing/README.md` и
`docs/testing/smoke.json`; команды выполняются из его корня. Если skill установлен
глобально, сначала найди этот репозиторий по текущему workspace. Для других
проектов не применяй команды и сценарии Cosplay 2.

1. Сопоставь затронутую бизнес-логику с существующими тестами. При запросе на
   расширение покрытия добавь содержательные unit/integration тесты в модули
   владельцев логики. Используй kotlin.test, существующие fakes и зависимости;
   сеть в code tests исключена. До первого запуска проверь сигнатуры и ожидания.
   Зафиксируй первый результат честно: требование «с первого запуска» не разрешает
   скрывать ошибки или выдавать повторный запуск за первый.
2. После новой фичи сначала обнови затронутые smoke-шаги и ожидания по реальному
   контракту. Сохрани проверку базовых сценариев. Укажи установленный build/version:
   локальная сборка из PR и задеплоенная пользователем сборка — разные объекты проверки.
3. Запусти `scripts/verify.ps1 -OutputDirectory build/verification/<уникальный-run>`.
   Exit 2 при успешном коде означает ожидающий UI; exit 1 требует разбора журналов.
   Не меняй версии toolchain для обхода ошибки окружения. После изменения исходников
   нужен новый run. `run.json` задаёт revision/sourceHash для UI-отчёта.
4. Запусти настоящее приложение в отдельном тестовом профиле. Выбери доступный
   MCP: mobile для Android; Computer Use для Desktop. Playwright пригоден только
   для реально существующей web-цели, которой сейчас нет. Для Computer Use прочитай
   его skill и используй поддерживаемые API. При отсутствии MCP/устройства запиши
   BLOCKED с причиной, не подменяй MCP кодовыми Compose-тестами.
5. Пройди каждый шаг `smoke.json` через UI. Перед действием наблюдай текущий экран,
   после действия проверь ожидаемый результат и сохрани настоящий снимок в
   `<run>/screenshots/<step-id>.png`. Для окна с несколькими снимками сохраняй
   также модальные окна. Не используй координаты после изменения экрана без нового
   наблюдения. Не симулируй результат API и не подменяй настоящие снимки макетами.
   В FAIL укажи ожидаемое, фактическое, воспроизведение и вероятное место проблемы;
   зависимые невыполненные шаги — BLOCKED. После сбоя продолжай независимые сценарии.
6. Запиши `<run>/smoke.json` по формату README с точными revision/sourceHash из
   run.json. Запусти `scripts/verify.ps1 -OutputDirectory <run> -ReportOnly`.
   Дай ссылку на report.md, итоги обоих уровней и ограничения платформ.

При подготовке/обновлении PR выполняй оба уровня для текущих исходников; не
создавай PR/коммит и не публикуй отчёт во внешнем сервисе без запроса. GitHub workflow
выполняет кодовый уровень; MCP-прогон требует интерактивной сессии агента.
Зелёный code job не означает успешный полный цикл.
