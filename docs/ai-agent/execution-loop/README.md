# Execution Loop

Реализован последовательный runner для Codex CLI, а не фоновая автоматизация чата.
Статус: механизм подготовлен; измеряемые прогоны моделей пока не выполнены.
Результатов «первый vs второй» и «облако vs локально» пока нет.
Эксперимент независим от исторических v1/v2: их результаты не переименовываются.

При сверке с [примером дня 40](https://github.com/Dashkin-G/ai-advent-challenge-9-week-8/tree/task-day-40)
учтены отдельный контекст задачи, внешнее управление очередью, ограничение времени
и свидетельство на каждый критерий. Фоновые очереди внутри исполнителя запрещены.
У примера есть специально написанные проверки check.py для всех 17 задач.
Здесь добавлены восемь независимых структурных проверок ресурсов, но проверяющий
каждого поведенческого критерия ещё не реализован:
runner проверяет актуальность тестов/UI-свидетельств и отдельный модельный review.
Это ограничение эксперимента; APPROVE модели не равно доказательству всех критериев.
Данные и результаты чужого прогона не переносятся в наши метрики.

## Пул и запуск

Текущий источник — **Notion**, база
[cosplay-2 — мини-задачи](https://app.notion.com/p/20b2780b8c5a42799a68e5017a04b9a7),
пул `cosplay2-mini-2026-10-28`: 15 небольших задач интерфейса. В базе есть порядок,
тип, статус, критерии, файлы, проверка и явные зависимости; доска сгруппирована
по статусам. Карточки созданы по фактическому коду, но ещё не выполнялись.

Настройки — [source.json](source.json). Подключён режим `mcp-snapshot`: очередь
читается подключёнными инструментами Notion, затем сохраняется полный ответ
{dataSourceId, exportedAt, has_more:false, results:[...]} под build/execution-loop.
Это явный снимок, не скрытый fallback и не live polling. При изменении карточек
обнови экспорт через навык execution-loop до нового прогона; для сравнения моделей
передавай один и тот же зафиксированный пул. В новом checkout снимок нужно
скопировать или снова выгрузить из Notion. В Git хранятся только ID базы и настройки.

Для самостоятельного чтения без MCP укажи `transport: "rest"` и передай NOTION_TOKEN
через окружение, предоставив интеграции read-доступ к базе. OAuth подключённого
приложения не передаётся Node-процессу. REST использует data_sources/query,
Notion-Version 2025-09-03, пагинацию и фильтры проект/пул/статус. Токены не сохраняются
в source.json, снимке или отчёте. API сверено с
[официальным описанием](https://developers.notion.com/reference/query-a-data-source).
Текущий рабочий экспорт получен через MCP; REST проверен тестами с подставными ответами.
Загрузчик не меняет статусы и не отмечает карточки выполненными автоматически.

Для Notion нужны точные поля созданной базы: ID (MCP: userDefined:ID), Задача,
Проект, Пул, Порядок, Тип, Статус, Критерии, Файлы, Проверка, Зависимости.
Используются только карточки cosplay-2 нужного пула в статусе «Готово к работе».
ID не перенумеровываются; зависимости должны ссылаться на предыдущие готовые
карточки этого же пула. Недостающие критерии/дубли/меньше 15 задач блокируют загрузку.

**GitHub Issues** также поддерживается: настрой type=github, repository=
Flobsterable/cosplay-2, label=execution-loop и limit=20. Берутся открытые Issues от старых к новым;
pull requests исключаются. Загрузка идёт один раз перед прогоном, далее используется
фиксированный снимок. Удалённые изменения во время прогона его не меняют.

Для подходящей Issue нужны метка `execution-loop`, ровно одна метка типа
`type:bug`, `type:feature`, `type:refactor`, `type:test` или `type:docs`,
и непустой раздел описания `## Критерии готовности` (также поддерживается
`## Acceptance criteria`). Всё описание сохраняется как контекст задачи.
Например, тело Issue с метками `execution-loop` и `type:bug`:

```markdown
## Описание
При baseUrl=https://example.test/events/one ссылка /tickets склеивается неверно.

## Критерии готовности
- [ ] Результат — https://example.test/tickets.
- [ ] Регрессионный тест воспроизводит причину и проходит после исправления.
```

Метки создаются и назначаются в GitHub. Загрузчик только читает Issues:
не создаёт, не комментирует и не закрывает их. Неподготовленная задача в выбранных
первых 20 останавливает подготовку с указанием номера. Для эксперимента нужно
15–20 подходящих задач; при меньшем числе запуск не начинается. Автоматической
подмены локальным пулом нет. Публикация подготовленных задач требует отдельного запроса.

Для CLI используется GitHub REST API без `gh` и новых библиотек; авторизация
подключённого GitHub в чате не передаётся отдельному Node-процессу. Для публичного
репозитория можно читать анонимно в пределах лимитов GitHub. Для приватного
репозитория/большего лимита передай `GITHUB_TOKEN` или `GH_TOKEN` через окружение
процесса с доступом Issues: read. Значение не входит в снимок и отчёты.
Поведение API сверено с [официальным описанием Issues](https://docs.github.com/en/rest/issues/issues#list-repository-issues).

[tasks.json](tasks.json) сохранён как **локальный пример** из 18 задач: 4 бага, 3 небольшие фичи,
3 рефакторинга, 4 задачи на тесты и 4 на документацию.
Задачи выполняются в порядке EL-01…EL-18; некоторые используют результаты предыдущих.
Каждая содержит бинарный критерий приёмки. Баги основаны на чтении исходников,
а не на выполненном воспроизведении; при исполнении нужен RED → исправление → GREEN.
Состояние каждой задачи хранится в журнале прогона, исходный пул не редактируется.

Нужны Node.js (в среде подготовки v24.20.0), git, установленный и авторизованный
Codex CLI, JDK/Android SDK и MCP из [инструкции тестирования](../../testing/README.md).
Используй отдельный чистый checkout. Runner намеренно отклоняет грязное дерево,
не делает reset/clean. В режиме draft-pr создаёт только ветки результатов. Перед первым прогоном подготовку следует
сохранить отдельным коммитом по запросу пользователя, чтобы runner и пул входили в baseline.

Из корня такого checkout:

```powershell
node scripts/execution-loop.mjs validate
node --test scripts/execution-loop*.test.mjs
node scripts/execution-loop.mjs fetch build/execution-loop/pool-1.json
node scripts/execution-loop.mjs preflight
node scripts/execution-loop.mjs run notion-1
node scripts/execution-loop.mjs run cloud-1 <точный-id-модели> cloud 30 build/execution-loop/pool-1.json
node scripts/execution-loop.mjs run local-1 <точный-id-локальной-модели> ollama 30 build/execution-loop/pool-1.json
```

Для сравнения используй один и тот же снимок (скопируй его в каждый checkout).
`fetch` не меняет код и не запускает модель. Запуск без пути к снимку сам читает
выбранный источник из source.json; это удобно для отдельного прогона:

```powershell
node scripts/execution-loop.mjs run cloud-1 <точный-id-модели> cloud 30
```

Для явного запуска локального примера:

```powershell
node scripts/execution-loop.mjs run example-1 <точный-id-модели> cloud 30 docs/ai-agent/execution-loop/tasks.json
```

Команды `run` запускают реальные изменения и коммиты; выполняй их
в разных checkout от одного baseline. Локальная модель должна уже обслуживаться
Ollama; допустим также провайдер `lmstudio`. Runner не устанавливает модель.
Права исполнения наследуются из настроек Codex; runner задаёт `-a never`, чтобы
запрос разрешения завершался отказом, а не ожиданием человека. Права не расширяются.
Если разрешения не позволяют работать автономно, это ограничение окружения,
а не основание включать bypass. Без аргумента модели используется текущая настройка
Codex (в run.json — default); точный ID лучше передавать для контролируемого сравнения.
Для Ollama/LM Studio точный ID обязателен.

Механизм использует [codex exec и структурированный ответ](https://learn.chatgpt.com/docs/non-interactive-mode)
и [локального провайдера OSS](https://learn.chatgpt.com/docs/config-file/config-advanced).
Команды сверены также с локальным `codex exec --help`; доступность модели этим не проверена.
В новом чате проекта навык вызывается как `$execution-loop` после обновления каталога
skills. Пользовательский config.toml не изменяется, глобальная установка не требуется.

## Как работает цикл

1. Снимок пула, инструкций, baseline SHA, модели и провайдера сохраняется в
   `build/execution-loop/<run-id>`. Существующий каталог не перезаписывается.
   GitHub-снимок также содержит URL/номер/updatedAt каждой Issue и время выборки.
2. Для задачи создаётся отдельный detached worktree от текущего успешного кода.
   Для текущего мини-пула [mini-recipes.json](mini-recipes.json) задаёт 15 готовых
   одношаговых планов с предметными навыками. Они применяются только при совпадении
   источника и SHA-256 полного контракта задачи; смена текста, описания или
   зависимостей возвращает обычное планирование, а не использует старый план.
   Для docs runner создаёт один шаг локально, сохраняя явные зависимости и EL-ID
   из требований. Если есть неизвестная ссылка, вызывается планировщик. Для кода
   read-only планировщик выбирает профиль, зависимости и 1–6 проверяемых шагов
   с именами существующих repo skills. Исполнитель каждого шага — новая сессия
   Codex; в контекст передаются исходная задача, план и результаты завершённых шагов.
   Последний шаг проверяет всю задачу. План сохраняется в `<EL-XX>/plan.json`.
3. Для кода обязателен two-level-testing: сборка/тесты/Lint и MCP smoke со снимками.
   Затем runner повторно запускает `verify.ps1 -ReportOnly`, проверяющий текущие
   исходники и свидетельства. Для Markdown-задач выполняется `git diff --check`.
4. После проверок запускается независимое read-only ревью в новой сессии.
   Оно получает исходную задачу, план, весь diff (включая untracked), handoffs
   и каталог свидетельств. Подтверждённые findings возвращаются обработчику и
   исполнителю; затем повторяются финальный шаг, проверки и независимое ревью.
   Только задача с APPROVE, прошедшими проверками и реальным diff получает локальный
   коммит `EL-XX: <название>`. Он переносится через cherry-pick в основной checkout;
   следующие задачи стартуют от него. Незавершённый diff туда не переносится.
5. При сбое отдельная сессия обработчика читает журналы, различает локальную
   и общую причину и выбирает retry/skip/stop. После исправления повторяется
   сбойный шаг, затем финальные проверки. Неудача финальной проверки повторяет
   последний шаг. После skip продолжаются независимые задачи, зависимые получают
   BLOCKED до исполнения. Связи определяются планом по исходным требованиям.
6. Невосстановимый общий сбой, повтор общей причины, ошибка обработчика,
   изменение инструкций/HEAD вне runner или вмешательство человека останавливают
   очередь. Артефакты и неудачные diff сохраняются. Закрытия Issues и изменения
   статусов Notion нет; результат хранится в отчёте с ссылкой на PR.

## Отдельный draft PR на задачу

[publication.json](publication.json) включает `mode=draft-pr` для Flobsterable/cosplay-2.
После локальных проверок, APPROVE и коммита runner создаёт ветку
`codex/execution-loop/<run-id>/<el-id>`, отправляет её и открывает draft PR.
Задача становится DONE после подтверждения PR. Автослияние выключено.
В описание входят критерии, ссылка на Notion и сводка проверок; произвольные
команды и логи модели туда не копируются. Локальный отчёт не является артефактом CI.

Стратегия — **линейная цепочка всех успешных задач**, включая независимые:
первый PR направлен в `codex/two-level-testing`, следующий — в ветку предыдущего PR.
Так каждый diff содержит одну задачу, хотя рабочий код накапливается последовательно.
Сливать нужно по порядку, перенацеливая оставшиеся PR при необходимости.
Исходная ветка содержит настройку цикла и тестирования, поэтому первый PR
не направлен сразу в develop. Если очередь запускается из другой ветки,
явно измени baseBranch в конфигурации до прогона.

`preflight` проверяет очередь, Git remote, текущую ветку и GitHub push-доступ
без модели, push и создания PR. Авторизация — GH_TOKEN/GITHUB_TOKEN либо Git
Credential Manager; значения не пишутся в отчёты. При фактическом `run` runner
сначала отправляет точный baseline в исходную ветку обычным push; force не используется.
Отказ этого push останавливает запуск до первого обращения к модели.

Публикация имеет максимум две автоматические попытки без обращения к модели.
Перед созданием PR ищется существующий PR с теми же head/base; после неопределённого
результата POST выполняется повторное чтение. Закрытый или несовпадающий PR
не заменяется. При постоянной ошибке очередь останавливается, коммит и фаза
публикации сохраняются. Повтор всей кодовой задачи для исправления GitHub не запускается.
Автоматического возобновления остановленного прогона пока нет: сначала аудит журнала.

`artifacts.json` содержит ссылки всех подтверждённых PR, также при остановке.
При запуске из чата навык execution-loop прикрепляет каждую ссылку к текущему чату
через attach_artifact. Самостоятельный Node-процесс оставляет ссылки в файле и отчёте.
Для эксперимента без публикации поставь `mode=local`; этот режим сохраняет
локальные коммиты и не требует GitHub-доступа. При сравнении используй одинаковый режим.

## Экономия обращений и контекста

По умолчанию действует [economy.json](economy.json): максимум **36 CLI-вызовов
на прогон**, **6 на задачу**, до **6 000 символов в передаваемом prompt**,
**8 минут на одну сессию** и мягкий порог **120 000 токенов, сообщённых CLI**
с резервом 10 000 перед следующим вызовом. Лимиты включают планирование,
исполнение, ревью и восстановление. При достижении порога очередь останавливается
без ещё одного обращения к модели для объяснения Budget. `maxReportedTokens=0`
отключает только токеновый порог; лимиты вызовов остаются.

Токеновый порог и резерв проверяются между вызовами и не являются жёстким ограничением
одного ответа: текущий вызов может превысить остаток. При отсутствии usage
`stopOnMissingUsage=true` блокирует следующий вызов без платной диагностики.
`callsWithoutUsage` показывает неизвестные вызовы. Превышение лимита времени
сессии тоже останавливает цикл без вызова восстановления. Это не расчёт денег,
не лимит счёта провайдера и не процент оставшейся подписки.

Экономия достигается так:

- Текущий зафиксированный мини-пул исполняется за **30 сессий вместо 44**
  в обычном успешном случае: исполнитель и независимое ревью для каждой задачи,
  без отдельного планировщика. 36 сессий включают резерв на восстановление.
  Это расчёт числа сессий, не замер экономии токенов и не число HTTP-запросов.
  Один Codex CLI-вызов может обращаться к модели многократно. Неизвестные,
  изменённые и большие задачи по-прежнему планируются моделью и делятся на шаги.
- docs исполняются за два вызова — один рабочий шаг и независимое ревью;
  план создаётся локально. Зависимости берутся из dependsOn и явных EL-ID.
  Для кода оптимизация применяется только по зафиксированному mini-recipe. Для сравнения можно
  отключить `directDocs`, вернув отдельный планировщик.
- Пять импортированных SKILL.md сокращены с 76 114 до 5 116 символов суммарно
  (93,3%); прежний материал сохранён как references/upstream-reference.md с
  отдельными хэшами. Это измерение текста, не доказанный процент экономии токенов.
- История планировщика содержит ID/названия/статусы, а не все старые критерии.
  Исполнитель получает последний краткий handoff, ревью — последнее ревью;
  полные данные каждого этапа остаются в context.json. Большие payload не
  обрезаются: вместо них prompt содержит ссылку и требование прочитать критерии
  из файла. Порог prompt не ограничивает дальнейшие чтения модели.
- Результаты и журналы не пересказываются целиком; нужны точечные чтения через
  rg/диапазоны. Большая задача по-прежнему делится на шаги, ревью и проверки
  не пропускаются. Модель и reasoning автоматически не переключаются.
- Во всех сессиях передаётся `tool_output_token_limit=1500`: ограничивается
  объём каждого вывода инструмента в истории. Это поддерживаемая настройка
  из [официальной конфигурации Codex](https://learn.chatgpt.com/docs/config-file/config-sample).
  Полные логи остаются на диске. Настройки пользователя, системные инструкции
  и обязательные правила проекта не обрезаются ради экономии.

До ревью выполняются локальные проверки без модели: зависимости всего пула и
Git-подпись до запуска; затем конфликтные маркеры, пробелы (включая новые файлы),
битые относительные ссылки в добавленных строках Markdown и опасные untracked symlinks.
Восемь mini-recipe проверяют нужный текст в ресурсах своего UI-модуля и наличие
ссылки на ресурс в Kotlin. Проверки отклоняют все восемь исходных незавершённых
изменений. Это структурные проверки, они не доказывают правильность callback,
позиции элемента или состояния интерфейса; code tests, MCP smoke и ревью обязательны.
Итог сохраняется в `<EL-ID>/local-checks.json` и передаётся ревьюеру.
При ошибке такой проверки runner сам выбирает ограниченный retry последнего шага
с точным отчётом: дополнительная сессия `recover` не расходуется. Лимиты повторов
и предохранитель повторяющейся причины остаются.

В run.json/modelCalls записываются этап, размер prompt и полного контекста,
размер обязательных навыков, статус вызова и usage (input/cache/output).
Учёт основан на [codex exec --json](https://learn.chatgpt.com/docs/non-interactive-mode),
событиях turn.completed, без оценки токенов по символам. stdout JSONL сохраняется
в agent.log, stderr — отдельно в agent.log.stderr.log. Полный расход внутренних
шагов модели ограничивается её настройками и timeout; runner не отключает инструменты.

## Навыки и восстановление

| Этап | Навык | Ответственность |
| --- | --- | --- |
| Очередь | [execution-loop](../../../.agents/skills/execution-loop/SKILL.md) | Запуск протокола, отчёт и границы эксперимента |
| План | [execution-loop-plan](../../../.agents/skills/execution-loop-plan/SKILL.md) | Декомпозиция, профиль, зависимости и предметные skills |
| Шаг | [execution-loop-step](../../../.agents/skills/execution-loop-step/SKILL.md) | Одно изменение в отдельном контексте, проверка контракта |
| Сбой | [execution-loop-recover](../../../.agents/skills/execution-loop-recover/SKILL.md) | Диагноз, локальное исправление и выбор дальнейшего действия |
| Ревью | [execution-loop-review](../../../.agents/skills/execution-loop-review/SKILL.md) | Отдельная read-only сессия: APPROVE / REQUEST_CHANGES / BLOCKED |

В основу этапов включены пять навыков из
[addyosmani/agent-skills](https://github.com/addyosmani/agent-skills), MIT,
commit `aeac41d4d005999432bb7312f7ff06383a91d59d` (0.6.13).
Они установлены локально в `.agents/skills/` и адаптированы к Cosplay 2:
planning-and-task-breakdown → план; incremental-implementation → шаг;
debugging-and-error-recovery → сбой; code-review-and-quality + profile-review → ревью;
context-engineering → передача состояния всех этапов.
[Манифест источника](upstream-skills.json) хранит upstream blob SHA и SHA-256
адаптированных файлов (UTF-8, нормализация переводов строк в LF);
копия MIT license лежит рядом с каждым навыком.
Обновление источника выполняется отдельно между прогонами, не при старте задачи.

Адаптация явно заменяет параметры хоста исходных навыков: второй трекер
tasks/todo.md не создаётся, разрешённый автономный прогон не требует повторного
подтверждения плана человеком, коммиты делает только runner, npm/React-примеры
не заменяют реальные Gradle/KMP-проверки. Ревью не выполняет пишущие мутационные
тесты из upstream: возможный пробел покрытия возвращается исполнителю.
Пользовательские разрешения и необходимость подтверждения новых внешних действий
не расширяются установкой навыков. Остальные upstream skills/plugin не установлены.

Все этапы выполняются последовательно. Это разные CLI-сессии и skills,
а не постоянно растущий контекст одного исполнителя. Чтение предметных навыков
задаётся инструкциями; runner проверяет существование файлов выбранных skills,
но не доказывает их фактическое соблюдение моделью.

Политика восстановления зафиксирована для всех моделей:

- На планирование/исполнение/проверки задачи — общий бюджет 30 минут по умолчанию.
  Диагностика тоже расходует этот бюджет. Для завершения диагностики обработчик
  имеет отдельный timeout до 5 минут на вызов; максимум два вызова на задачу.
  Максимум три попытки выполнения задачи, без рекурсивного запуска обработчиков.
- `scope=task`: исправить конкретный шаг и retry; если требуется уточнение — skip.
  После исчерпания попыток такая задача BLOCKED, независимая очередь продолжается.
- `scope=shared`: проверить доступную настройку/инициализацию и retry только после
  проверки устранённой причины. Если та же причина повторилась после восстановления,
  срабатывает предохранитель. Общий лимит — две разные общие причины на прогон;
  третья останавливает очередь, даже если модель меняет fingerprint.
  Кроме того, три одинаковых fingerprint среди всех инцидентов останавливают
  очередь даже при классификации причины как локальной.
- `scope=runner`: сохранить диагноз и stop. Сам runner и его инструкции не
  переписываются работающим процессом; его патч проверяется отдельной задачей
  с новым запуском. Сбой обработчика тоже приводит к stop, а не к падению всей очереди.

Обработчик не меняет зависимости, версии, права, секреты и критерии приёмки для
обхода ошибки. Общая недоступность auth/провайдера/MCP не считается 18 отдельными
неудачами задач: очередь останавливается на общей причине. Начальная загрузка
GitHub и проверка чистоты checkout выполняются до этапов задач; при их ошибке
задачи не стартуют, восстановление модели не вызывается.

Worktrees и свидетельства даже успешных задач сохраняются под
`build/execution-loop/<run-id>/<EL-XX>/workspace`. Сначала экспортируй нужные
логи/снимки и проверь незакоммиченный diff; затем удаляй рабочие копии через
`git worktree remove <путь>`. Удаление каталога build без снятия worktrees оставит
устаревшие регистрации Git. В рабочих копиях не будет нетрекаемого local.properties
основного checkout: SDK передаётся через обычные ANDROID_HOME/ANDROID_SDK_ROOT
или настраивается в тестовой копии без публикации локальных значений.

В одном checkout действует эксклюзивная блокировка в git-каталоге. После аварийного
завершения проверь отсутствие работающего процесса/его инструментов и сохранность
diff перед ручным удалением `execution-loop.lock`; автоматически lock не сбрасывается.
При timeout или Ctrl+C runner завершает дерево дочернего процесса и пишет STOPPED.
Принудительное закрытие терминала/питания может оставить RUNNING и требует аудита.

Приёмку по смыслу и firstPass сообщает модель: runner не является независимым
семантическим ревьюером и не доказывает отсутствие регрессий. Он проверяет
git/проверки/свидетельства. Логи могут содержать серверные данные: до публикации
проверяй их, не включай секреты. Артефакты лежат под игнорируемым build/.

Автотесты runner используют временные Git-репозитории и подставные ответы Codex.
Они проверяют порядок этапов, перенос коммитов, возврат findings, повторы и
предохранители; не доказывают качество реальных ответов модели или работу UI.
Валидация навыков проверяет их формат; следование инструкциям проверяется
отдельным фактическим прогоном. Сборки приложения при изменениях только этого
механизма не выполнялись.

## Измерения

`run.json` хранит время начала/окончания, durationMs, профиль, firstPass, коммит
или причину, шаги, попытки, путь к worktree и общий журнал incidents.
Каждый вызов plan/work/recover/review хранит собственные prompt/schema/result/agent.log.
Шаги содержат handoff: summary, files, decisions, risks и verification с command/result.
Все вердикты ревью и fingerprint рассмотренного diff сохраняются в reviews,
включая неудачные; APPROVE с findings или REQUEST_CHANGES без findings отклоняется.
Runner сравнивает HEAD, diff, index и untracked содержимое до/после ревью; изменение
дерева ревьюером останавливает прогон. Ревьюер наследует выбранную модель:
независимость означает отдельный контекст, а не гарантированно другую модель.
`report.md` — таблица «задача → результат → минуты» и перечень обработанных сбоев.
Во время работы RUNNING в журнале обозначает незавершённую задачу; после аварийного
закрытия процесса такой журнал нельзя считать завершённым прогоном.

Главная строка отчёта:

```text
Количество времени без пауз: <фактическое число> мин
```

Это wall-clock от старта цикла до остановки/завершения пула,
включая тесты, планирование, восстановление, автоматические исправления и
пропущенные локально заблокированные задачи. Автоматическое восстановление
не является паузой человека. Текущий протокол версии 6 добавляет готовые mini-планы,
локальные проверки и строгую остановку при неизвестном usage; версия 5 добавила публикацию PR;
версия 4 включает экономный контекст и лимиты; версия 3 добавила независимое ревью, версия 2 — восстановление,
версия 1 — stop-on-first-failure:
нельзя смешивать результаты этих версий; compare отклоняет такое сравнение.
Человек не вмешивается между задачами; любое вмешательство завершает измерение.
Число DONE подряд — успешный префикс до первой незавершённой задачи.
Отдельно считаются totalDone и recoveryCount, чтобы пропуски и исправления
не выдавались за непрерывную серию полностью выполненных задач.
Среднее время — сумма времени DONE / число DONE; при нуле DONE значение null.
Процент с первого раза — DONE с firstPass=true / все начатые задачи × 100;
ожидаемый RED регрессионного теста до исправления не считается провалом попытки.
Провал первой проверки решения после исправления считается; последующий успех
не возвращает firstPass=true. Первичные логи сохраняются в каталоге задачи.

## Второй прогон и облако vs локальная модель

После остановки изучи логи и зафиксируй категорию причины: контекст, код,
зацикливание/timeout, окружение/MCP, лимиты провайдера, вмешательство человека.
Не объявляй сбой окружения дефектом модели. Между прогонами внеси узкую правку
правил/профиля по наблюдению; запиши «причина → изменение → ожидаемый эффект».
Не меняй пул или критерии готовности для облегчения второго прогона.

Cloud-2 стартует от того же исходного кода, что cloud-1, с обновлёнными инструкциями.
Не запускай его поверх исправленных 18 задач. Сохрани diff инструкций и SHA отдельно.
Версии, машина, MCP, порядок, модель, reasoning, лимиты и состояние кэшей должны
быть одинаковыми или явно указанными как различия. Фиксируй разрешённые параметры
окружения отдельно; не копируй config.toml целиком с возможными секретами.
Для локальной модели повтори пул от такого же baseline с теми же правилами;
фиксируй имя/квантование модели, backend, GPU/RAM и контекст. В идеале выполни
local-1 и local-2 для обеих конфигураций правил.

```powershell
node scripts/execution-loop.mjs compare <каталог-cloud-1> <каталог-cloud-2> <каталог-local-1>
```

Сравнение отклоняет незавершённые журналы и разные хэши пула. Различие baseline
предупреждается, но эквивалентность исходного кода требует проверки: изменение
только инструкций тоже меняет SHA. Отдельно сравни минуты и DONE подряд: более
медленная модель может работать дольше, выполнив меньше задач. Рост минут:
`cloud-2.minutes - cloud-1.minutes`; относительный рост при ненулевом cloud-1:
`(cloud-2.minutes / cloud-1.minutes - 1) × 100%`. До фактических прогонов — «нет данных».
