# Два уровня тестирования

Уровень 1 проверяет бизнес-контракты без реальной сети. Новые собственные тесты
есть в `core/model` (JSON/обязательные поля/статус), `data/festival` (HTML/ссылки),
`data/update` (выбор APK/ошибка/отмена). Существующие `composeApp` и `core/platform`
проверяют каталог, кэш, отмену, избранное, город, storage и Compose UI.
Это карта выбранного покрытия, а не измеренный процент покрытия всех модулей.

Уровень 2 — пять сценариев в [smoke.json](smoke.json), всего 21 шаг:
поиск, год/месяц, избранное/детали/удаление, город, поддержка/черновик.
У приложения нет логина и создания фестиваля. В качестве изменяемой сущности
проверяется запись избранного, созданная в изолированном тестовом профиле.
Сценарии выполняет агент через MCP, наблюдая реальный UI и делая снимок каждого шага.

Первый фактический прогон сохранён в [отчёте от 24 октября 2026](evidence/2026-10-24/report.md):
69 тестов, обе компиляции, Android Lint, 5 Desktop MCP smoke-сценариев и 30 снимков.
Это снимок локального прогона рабочих изменений; Android UI и удалённый CI в него не входят.

## Запуск полного цикла в Codex

Skill доступен в `.agents/skills/two-level-testing`. Установка также в личный Codex:

```powershell
.\.codex\install-testing.ps1
```

Промпт для расширения покрытия:

> Используй $two-level-testing. Найди бизнес-модули без собственных тестов,
> добавь содержательные unit/integration тесты минимум в 3 файла 3 модулей.
> Проверь сигнатуры и ожидания до первого запуска, запусти тесты и честно запиши
> первый результат. Затем пройди все smoke-сценарии через MCP и сформируй единый
> отчёт со снимком каждого шага. Для падений укажи вероятное место проблемы.

Промпт после PR:

> Используй $two-level-testing для текущего PR: сопоставь тесты с изменёнными
> контрактами, выполни кодовый уровень и все MCP smoke-сценарии для текущих
> исходников. Сохрани единый отчёт со скриншотами; ничего не публикуй.

Промпт после новой фичи:

> Я задеплоил новую фичу: <описание>. Используй $two-level-testing: определи
> проверяемую сборку, обнови затронутые smoke-сценарии и тесты, прогони оба уровня
> заново и сохрани единый отчёт со скриншотами. Для недоступной сборки укажи BLOCKED.

Команды из корня, Java launcher должен быть установлен и совместим с Gradle;
daemon/toolchain закреплены на Java 21. Нужен Android SDK 37.

```powershell
.\scripts\verify.ps1 -OutputDirectory build/verification/run-001
# После MCP-прогона и сохранения smoke.json:
.\scripts\verify.ps1 -OutputDirectory build/verification/run-001 -ReportOnly
```

Первый вызов запускает тесты пяти модулей, компиляцию Android/Desktop и Android Lint,
сохраняет exit codes, журналы, снимок JUnit XML и report.md. Новый цикл использует новую
папку; повторное использование папки с run.json отклоняется.
`OutputDirectory` задаётся относительно корня репозитория, как в примерах выше.
При необходимости используется `-GradleInitScript docs/build-upgrade/maven-mirror.init.gradle.kts` —
существующее зеркало, а не изменение версий. Наличие старого XML при упавшей команде
не считается доказательством успеха. Отчёты в build игнорируются Git.

Exit 0 — оба уровня подтверждены; exit 1 — код/сборка не подтверждены;
exit 2 — код прошёл, UI имеет FAIL/BLOCKED или ещё не выполнен.
`-CodeOnly` проверяет exit code только первого уровня для CI, но полный цикл
остаётся BLOCKED до MCP-прогона. Изменение исходников или плана smoke после запуска
делает старый отчёт непригодным: проверяются commit и SHA-256 файлов кода/конфигурации
и smoke.json, включая новые неигнорируемые файлы. Это привязка локальных свидетельств,
не криптографическая аттестация действий агента.

## MCP и тестовый профиль

Доступные платформы — Android и Desktop JVM. Для Android нужен подключённый mobile
MCP с наблюдением, кликами, вводом и screenshots и устройство/эмулятор. Для Desktop
подходит MCP Computer Use (`node_repl` + `@oai/sky`). Playwright MCP предназначен для
web; web-цели здесь нет. Наличие сценариев или эмулятора не доказывает подключение MCP.
При отсутствии инструмента/сборки указывается BLOCKED, причина и способ разблокировки.

На Windows Desktop запускайте приложение отдельным процессом с APPDATA, указывающим
на `<run>/appdata`, чтобы избранное и город не затрагивали личные данные:

```powershell
$env:APPDATA = Join-Path (Get-Location) 'build/verification/run-001/appdata'
.\gradlew.bat :composeApp:run
```

Меняйте переменную только в процессе запуска; закройте тестовое окно после прогона.
На Linux аналогично задайте XDG_DATA_HOME. На Android используйте выделенный тестовый
эмулятор/профиль, не сбрасывайте личные данные. Перед S03 убедитесь, что избранное пустое.
Не запускайте установку обновлений, внешние отправки и покупку билетов в этих smoke.
Серверный fallback не подтверждает сетевой успех S01; при fallback отмечайте S01 FAIL
или BLOCKED по причине. Скриншот не доказывает запрос active_year — это проверяют
кодовые тесты. Android back/клавиатура требуют отдельного прогона на Android;
Desktop smoke их не подтверждает.

В сценарии города «Только мой город» означает переключатель «Мой город: <город>»;
«Все города» отключает фильтр. Сохранение города автоматически включает фильтр,
поэтому при проверке явного включения сначала выберите «Все города».

## Формат результата MCP

Агент записывает `<run>/smoke.json`. revision/sourceHash берутся из run.json.
Один результат на каждый сценарий и шаг плана; ниже только пример одной записи,
при настоящем прогоне нужны все 5 сценариев и все 21 шаг.

```json
{
  "revision": "<из run.json>",
  "sourceHash": "<из run.json>",
  "platform": "Desktop Windows",
  "transport": "MCP Computer Use / node_repl / @oai/sky",
  "build": "локальная сборка текущих исходников, версия ...",
  "scenarios": [{
    "id": "S01",
    "status": "PASS",
    "diagnosis": "",
    "steps": [{
      "id": "S01-1",
      "status": "PASS",
      "actual": "Каталог загрузился с сервера, видны карточки",
      "screenshot": "screenshots/S01-1.png"
    }]
  }]
}
```

Для каждого шага фиксируются наблюдаемое поведение и PASS/FAIL/BLOCKED, для каждого
выполненного шага — снимок. Снимки хранятся внутри run; при модальных окнах сохраняйте
дополнительные изображения и упоминайте их в actual/diagnosis. Генератор не допускает
полный PASS без всех уникальных шагов, результатов PASS и существующих снимков.
Агент проверяет содержимое снимков визуально. Для FAIL описывает ожидание, факт,
повторение, вероятный файл/слой и уверенность; сетевые/инструментальные проблемы
отделяет от дефекта приложения. Исправление поведения — отдельная задача Bug Fix,
после исправления выполняется новый цикл.

## Flow разработки и CI

При подготовке и обновлении PR агент применяет skill и выполняет оба уровня локально.
`.github/workflows/verification.yml` запускается на PR и вручную: code tests,
обе компиляции, Lint; сохраняет артефакт и сводку даже при ошибке.
Hosted runner не имеет интерактивной MCP-сессии Codex, поэтому UI в CI помечен
BLOCKED до локального агентского прогона. Workflow не запускает агента через API
и не публикует комментарии. Полностью автоматический удалённый MCP-прогон потребует
отдельного runner с агентом/устройством; здесь он не заявляется настроенным.
GitHub Actions проверяется после публикации изменений; локальный запуск не доказывает CI.
