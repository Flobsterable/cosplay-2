# Автоматическое обновление документации

## Когда меняется описание продукта

Документы в develop описывают только уже слитый туда код. Описание новых экранов
и пользовательских сценариев не добавляется заранее из открытой feature-ветки.
При мердже фичи агент сравнивает before..after, обновляет существующие
[features.md](features.md), [screens.md](screens.md) и другие затронутые документы
и публикует отдельный коммит в develop. До этого состояния README/docs служат
базой, по которой можно увидеть требуемые изменения документации.

## Запуск и проверка

После слияния PR в develop или main GitHub Actions запускает
[Update project documentation](../.github/workflows/docs-sync.yml).
Триггер — push в целевую ветку с изменениями Kotlin, Gradle, TOML, release.yml
или самого docs-sync.yml. Это охватывает merge, squash, rebase и прямые push кода,
в том числе слияния внешних PR. Сравнивается весь диапазон before..after push.
Агент анализирует изменения Kotlin/Gradle/release.yml, сам читает определения API,
места использования, README и docs. Он сохраняет нужные правки и создаёт коммит
прямо в ветке, куда влили PR. Отдельный PR документации и ручное слияние не нужны.

До коммита workflow запускает /sync --apply закреплённого runtime агента.
В нём [docs-verifier.js](https://github.com/Flobsterable/cosplay-dev-assistant/blob/5b112c6ec8927c245b4a3f0ca23d658fc0e3aab5/tools/dev-assistant/src/docs-verifier.js)
проверяет новые утверждения, параметры, API, примеры команд, относительные ссылки
и якоря. [sync-docs.js](https://github.com/Flobsterable/cosplay-dev-assistant/blob/5b112c6ec8927c245b4a3f0ca23d658fc0e3aab5/tools/dev-assistant/src/sync-docs.js)
отклоняет неполный контекст и проверяет результат до записи. Ошибка CLI останавливает
публикацию непроверенных изменений. При сбое генерации или проверки выполняются
до трёх попыток с паузой 15 секунд и свежим checkout. После третьей ошибки job
остаётся красным; причина доступна в Actions. Проверка статическая: команды приложения не исполняются.
Если документация уже актуальна или в диапазоне нет поддерживаемых изменений,
новый коммит не создаётся. Работа занимает время на запуск Actions и запросы модели.

Workflow использует существующие Secret LLM_API_KEY и Variables LLM_MODEL/LLM_BASE_URL,
как AI-ревью. Runtime закреплён на коммите 5b112c6ec8927c245b4a3f0ca23d658fc0e3aab5
репозитория Flobsterable/cosplay-dev-assistant. При обновлении агента нужно обновлять ref.
Токен GitHub Actions должен иметь contents:write; ограничения защиты ветки не обходятся.

В коммит включаются только README.md и Markdown в docs/. Код приложения, Gradle,
релизные теги и настройки workflow агентом не изменяются. Push только с README/docs
не проходит фильтр путей, поэтому собственный коммит не запускает новый цикл.
Уже обработанный диапазон определяется по Docs-Sync-Source в сообщении коммита.
Если целевая ветка изменилась во время генерации, workflow повторно анализирует
свежий checkout и заново генерирует правки; force push не применяется.
Если push отклонён при неизменной ветке (например, из-за защиты или прав), workflow
сразу завершается ошибкой, без повторных платных запросов генерации.

## Если обновление не выполнено

Отдельный job `Track documentation recovery` запускается после успешного,
ошибочного или отменённого job синхронизации, в том числе при сбое установки
зависимостей или таймауте основного job. При ошибке/отмене он создаёт GitHub Issue
«Документация не обновлена: <ветка> <SHA>» со ссылкой на запуск и точными base/head.
Повторные сбои того же диапазона обновляют эту задачу. Следующий мердж её не закрывает:
она остаётся видимым долгом до восстановления именно этого диапазона.

После устранения причины выберите Actions → Update project documentation →
Run workflow, ветку develop/main и base/head из задачи. Такой запуск использует
текущий исправленный workflow и закреплённый runtime. Re-run jobs подходит для
временного сетевого сбоя, но повторяет старую версию workflow/runtime.
Уже опубликованный диапазон пропускается по маркеру Docs-Sync-Source; force push
не применяется. Успешный повтор (включая результат «документация уже актуальна»)
автоматически закрывает задачу этого диапазона.

Логи каждой попытки, включая stderr, сохраняются как Actions artifact на 14 дней.
Непроверенные изменения не публикуются. Issue содержит только метаданные запуска,
а не ответы модели или содержимое логов. Job отслеживания имеет отдельные права
contents:read и issues:write; job генерации — только contents:write.
Если выключены Issues, нет прав issues:write или недоступен GitHub API, job
отслеживания тоже станет красным: проверьте оба job в Actions. Полная отмена
workflow или недоступность GitHub Actions может помешать запуску отслеживания;
это не гарантия доставки внешнего уведомления.
Локальную копию проекта на VPS нужно обновлять через git pull, чтобы /help читал свежие docs.
