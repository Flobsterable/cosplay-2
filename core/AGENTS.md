# Общие правила core

Целевая организация дополняет фактическую карту модулей в корневом AGENTS.md.

## Core: общие элементы и зависимости

- Размещай код по ответственности: `core/model` — общие модели и DTO,
  `core/network` — настройка сетевого клиента, `core/platform` — контракты
  и реализации платформенных возможностей. Бизнес-сценарии остаются в use cases,
  конкретные API и парсеры — в data, состояние экранов — у владельцев UI.
- Core не зависит от composeApp, feature или data. Сохраняй существующее
  направление зависимостей: `core/network` → `core/platform` → `core/model`.
  В core/model не добавляй Compose, платформенные SDK или зависимости от других
  модулей проекта. Наличие Compose в platform/network не разрешает размещать там
  обычные кнопки, карточки и оформление экранов.
- Выноси элемент в core, если у него общая ответственность и понятный контракт
  для потребителей. Использование на Android и Desktop внутри одного feature
  само по себе не делает элемент общим для приложения. Не создавай свалку
  `Utils.kt`, `Common.kt` или глобальных изменяемых объектов.
- Для новых групп элементов используй подпапки по назначению внутри текущего
  пакета: например `model/festival/`, `platform/storage/`, `platform/logging/`.
  Пакет соответствует пути; сохраняй одинаковую структуру общего контракта
  и платформенных реализаций. Не переноси существующие файлы без задачи.
- Публичный API core должен быть минимальным; детали реализации — internal/private.
  При изменении контракта проверь всех потребителей, сериализацию и сохранённые
  данные, если они затронуты. Изменение платформенного контракта проверяй
  на Android и Desktop; правила storage дополняет `core/platform/AGENTS.md`.

## Core UI: общие визуальные компоненты

- `core/ui` — целевое место общей дизайн-системы и компонентов разных feature.
  Сейчас такого Gradle-модуля нет. Выделяй его при задаче на общий UI, когда
  выявлены реальные потребители в нескольких feature; подключай только нужные
  Compose-зависимости и ресурсы, настраивай Android/Desktop. Изменение только
  этих инструкций не означает, что модуль уже создан.
- Компонент одного экрана остаётся в `ui/<экран>/components/`, нескольких экранов
  одного feature — в `ui/components/` этого feature. В core/ui выноси элементы
  без привязки к фестивалям, обновлениям или настройкам: общие кнопки, поля,
  диалоги, индикаторы и представления состояний. FestivalCard остаётся в feature.
- Корневой пакет нового модуля — `ru.flobsterable.cosplay2.core.ui`.
  Используй подпапки `theme/`, `components/button/`, `components/input/`,
  `components/dialog/`, `components/state/` по фактической необходимости.
  Самостоятельный компонент — отдельный файл; пустые папки заранее не создавай.
- Core UI не зависит от composeApp, feature, data, network или platform.
  Его API принимает простые данные, UI-параметры, slots и callbacks, а не
  FestivalSummary, feature UiState, repository, use case или state holder.
  Компоненты не запускают бизнес-сценарии и не управляют навигацией.
- Используй MaterialTheme и общие параметры дизайн-системы; не дублируй палитры
  и стили в feature. При выделении общей темы перенеси её из composeApp в
  `core/ui/theme/`, сохраняя внешний вид. Для компонентов предоставляй Modifier
  корневого элемента, понятную семантику доступности и поддержку disabled/error
  состояний там, где они применимы.
- Строки, принадлежащие общему компоненту, храни в ресурсах core/ui; тексты
  конкретного сценария передавай из feature параметром или slot. Проверь компонент
  в светлой/тёмной теме, при длинном тексте, увеличенном шрифте, узком окне
  и управлении клавиатурой на Desktop; явно укажи невыполненные ручные проверки.
